# بهبود عملکرد کلاینت و سرور

هدف، کاهش هزینهٔ پردازش هر بسته و واکنش بهتر به تغییر کیفیت ریزولر است. هیچ
تغییری در قالب بسته، رمزنگاری، احراز هویت یا اندازهٔ MTU این مرحله وجود ندارد.

ادامهٔ کار برای اتلاف زیاد، تأخیر و قطعی کوتاه در
[گزارش اینترنت ضعیف](weak-network-fa.md) آمده است.
کاهش بایت‌های کنترلی با حفظ رمزنگاری نیز در
[گزارش کاهش ترافیک](traffic-efficiency-fa.md) توضیح داده شده است.
کاهش CPU سرور برای هر بایت در [گزارش CPU سرور](server-cpu-fa.md) آمده است.

## تغییرات پیاده‌شده

- کدک Base36 دو رقم را در هر مرحله پردازش می‌کند. جدول ثابت encoder حدود
  ۲٫۵ کیلوبایت است و به‌جای تقسیم برای هر رقم استفاده می‌شود. این مسیر در
  ارسال query از کلاینت و دریافت آن در سرور استفاده می‌شود؛ قالب قبلی حفظ شده است.
- حالت‌های انتخاب ریزولر ۴، ۵ و ۶ از میانگین متحرک تأخیر با وزن ۱/۸ برای پاسخ
  تازه استفاده می‌کنند. شمارنده‌های قبلی برای آمار باقی می‌مانند. پنج پاسخ معتبر
  همچنان پیش‌نیاز استفاده از امتیاز تأخیر است.
- حالت ۶ امتیاز ریزولرها را برای حداکثر ۶۴ مسیر روی stack نگه می‌دارد و فهرست
  موقت را برای فیلتر اتلاف دوباره استفاده می‌کند. برای تعداد بیشتر، مسیر پویا
  همچنان وجود دارد. خواندن شمارنده‌های اتمیک غیرضروری نیز حذف شده است.

این تغییرات به نصب هر دو سمت به‌صورت هم‌زمان نیاز ندارند. افزایش سرعت کدک به
معنای افزایش همان درصدی سرعت اینترنت یا کاهش همان درصدی CPU کل برنامه نیست.

## نتیجهٔ اندازه‌گیری

محیط: Linux amd64، Go 1.27.1، `GOMAXPROCS=4`، AMD EPYC 9V74.
اعداد میانهٔ پنج اجرای ۴۰۰ میلی‌ثانیه‌ای، برای کد قبلی و جدید هستند.

| عملیات | قبل، ns/op | بعد، ns/op | کاهش زمان عملیات |
| --- | ---: | ---: | ---: |
| EncodeBytes، فریم ۱۲۸ بایتی | 359.1 | 220.0 | 38.7٪ |
| DecodeBytes، فریم ۱۲۸ بایتی | 297.9 | 244.2 | 18.0٪ |
| EncodeBytes، فریم ۵۱۲ بایتی | 1401.0 | 873.9 | 37.6٪ |
| DecodeBytes، فریم ۵۱۲ بایتی | 1085.0 | 925.8 | 14.7٪ |
| انتخاب مسیر، ۴ ریزولر، حالت ۶ | 296.5 | 248.9 | 16.1٪ |
| انتخاب مسیر، ۳۲ ریزولر، حالت ۶ | 1689.0 | 1446.0 | 14.4٪ |
| انتخاب مسیر، ۱۲۸ ریزولر، حالت ۶ | 6612.0 | 5608.0 | 15.2٪ |

تخصیص حافظهٔ انتخاب مسیر برای ۴ و ۳۲ ریزولر از ۳ به ۱، و برای ۱۲۸ ریزولر
از ۳ به ۲ کاهش یافت. برای ۳۲ ریزولر، حافظهٔ هر عملیات از ۶۴۰۰ به ۴۸۶۴ بایت رسید.

آزمون تغییر کیفیت مسیر، بعد از ۸۰۰ پاسخ پایدار و سپس ۳۲ پاسخ با کیفیت جدید،
انتخاب مسیر بهتر و سپس برگشت درست آن را بررسی می‌کند. نسخهٔ قبلی این آزمون را
پاس نمی‌کرد. یک پاسخ دیرهنگام به‌تنهایی در سناریوی آزمون باعث تعویض مسیر نمی‌شود.

تست انتها‌به‌انتها با چهار ریزولر شبیه‌سازی‌شده، تأخیر یک‌طرفهٔ ۱۰ میلی‌ثانیه،
نوسان تا ۲۰ میلی‌ثانیه و اتلاف ۱٪ در هر جهت اجرا شد. دریافت ۵۱۲ KiB در یک اجرا
از 317.8 به 352.1 KiB/s و دریافت موازی از 285.7 به 297.0 KiB/s رسید. این تست
تصادفی است؛ این دو مشاهده اثبات آماری افزایش throughput نیستند. برای ارزیابی
اینترنت واقعی، مسیر ثابت، چندین تکرار، بار یکسان و اندازه‌گیری CPU هر دو سمت
لازم است.

## اجرا و اعتبارسنجی

```sh
go test ./...
go test -race ./internal/client ./internal/basecodec ./server
go vet ./internal/client ./internal/basecodec
go test ./internal/basecodec ./internal/client -run '^$' \
  -bench 'BenchmarkLowerBase36Frame|BenchmarkBalancerLossThenLatency' \
  -benchmem -benchtime=400ms -count=5
MDNS_PERF=1 MDNS_PERF_DELAY=10 MDNS_PERF_LOSS=0.01 MDNS_PERF_IDLE=1 \
  go test ./server -run '^TestPerf$' -count=1 -v -timeout 5m
```

تست‌های تطبیق با فرمت قبلی، طول‌های صفر تا ۵۱۳ بایت، بخش پایانی کوتاه، صفرهای
ابتدایی، حروف بزرگ و کوچک و نویسهٔ نامعتبر در تمام موقعیت‌های فریم را بررسی
می‌کنند. تست‌های انتخاب مسیر، گزارش هم‌زمان پاسخ‌ها و مرز ۶۴/۶۵ ریزولر را نیز
پوشش می‌دهند.

برای استفاده از انتخاب مبتنی بر اتلاف و تأخیر تازه می‌توان در تنظیمات کلاینت
`RESOLVER_BALANCING_STRATEGY = 6` را انتخاب کرد. مقادیر پیش‌فرض تغییر نکرده‌اند.
صرفاً زیادکردن worker، duplication یا عمق pipeline الزاماً سرعت را بیشتر
نمی‌کند؛ ممکن است صف، اتلاف و CPU هر دو سمت را افزایش دهد.

## مسیر ادامهٔ کار

۱. پروفایل ظرفیت هر ریزولر: MTU، RTT، نوسان، خطاهای DNS و نرخ قابل‌تحمل را
   جدا نگه داریم؛ در صورت تغییر مسیر دوباره اندازه‌گیری کنیم. جلوگیری از
   کوچک‌شدن MTU همهٔ مسیرها به‌خاطر یک مسیر ضعیف، به طراحی قطعه‌بندی سازگار
   با پروتکل و آزمون ریزولرهای ناهمگون نیاز دارد.
۲. عمق pipeline و نرخ ارسال را با ظرفیت و RTT مسیر تطبیق دهیم؛ برای ریزولر
   حساس به نرخ، backoff داشته باشیم و برای مسیر بازیابی‌شده رشد تدریجی انجام دهیم.
۳. در Linux، دریافت و ارسال دسته‌ای UDP را با fallback قابل‌حمل بررسی کنیم.
   پروفایل نمونه سهم زیادی از زمان CPU را در syscall و هماهنگی runtime نشان
   می‌دهد؛ کاهش syscall باید با حفظ تأخیر پیام‌های کوتاه اندازه‌گیری شود.
۴. duplication را بر اساس اتلاف و نوع بسته تنظیم کنیم و CPU/بایت و تأخیر
   p95 را در کنار throughput بسنجیم؛ محافظت بسته‌های آغاز اتصال حفظ شود.
۵. ماتریس آزمون شامل ریزولر کم‌MTU، کند، محدودشونده با نرخ، پاسخ truncate،
   تغییر مسیر در حین انتقال، چند کاربر و دستگاه کم‌قدرت باشد.

این پنج مورد مسیر پیشنهادی ادامه هستند و در این تغییر پیاده نشده‌اند. سازگاری
با همهٔ ریزولرها قابل تضمین نیست: بعضی ریزولرها queryهای تونل را مسدود یا
دست‌کاری می‌کنند، یا zone موردنظر را resolve نمی‌کنند. تطبیق باید روی مسیرهایی
انجام شود که تبادل معتبر DNS را واقعاً عبور می‌دهند.
